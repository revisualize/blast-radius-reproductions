# blast-radius-reproductions

The experiments and calculations behind the quantitative demonstrations in
[What a Bounded Blast Radius Still Lets Through](https://revisualized.com/articles/what-a-bounded-blast-radius-still-lets-through),
runnable, in one file. It doesn't reproduce every number in the article: a
few, like the telemetry-exposure arithmetic in the rate section, are shown
worked in the prose itself rather than computed by a script, consistent
with the article's own evidence contract ("generated by the reproduction
script or an explicit calculation shown in the piece").

## Why this exists

The article makes seven distinct claims: a cap test, a dotfile enumeration
check, a parallelism-vs-observation-point table, a rename-vs-delete timing
comparison, a canary detection formula, a stratified-vs-random sampling
simulation, and a permission-boundary demonstration. None of them are worth
trusting on the page alone. This script produces each one for real, so the
numbers in the article are checkable rather than asserted. An earlier version
of this script only counted files and asserted a collapse rather than
executing one; that's fixed in section 1 below, caught in review, not by the
original drafting pass.

## Requirements

Requires GNU/Linux userspace specifically, not just any POSIX shell; several
sections depend on GNU userspace tools and util-linux utilities (`find -print0`, `mktemp -d` with a
template, `mv`'s cross-filesystem fallback, `setpriv`, `findmnt`) that aren't
portable to macOS or BSD userlands as written.

- Bash 4.2 or newer
- Python 3.9 or newer, specifically: section 3 calls
  `Executor.shutdown(cancel_futures=...)`, and `cancel_futures` was added in
  3.9. Preflight now checks this directly rather than only checking that
  `python3` exists, so a too-old interpreter fails immediately with a clear
  message instead of failing partway through section 3.
- GNU findutils, GNU coreutils
- util-linux, specifically `setpriv` (section 7 only, needs root) and
  `findmnt` (section 4, no elevated privilege needed). Both are provided by
  util-linux on systems that package it separately; the script degrades
  gracefully when either is absent (see "0. Preflight" below).
- **Section 7 requires root** (for `chown`/`setpriv`). Sections 1-6 need no
  elevated privilege. Running the whole script as a non-root user completes
  sections 1-6 normally and prints a message explaining why section 7 was
  skipped, rather than failing the run.

## Usage

```
chmod +x blast_radius_reproductions.sh
./blast_radius_reproductions.sh
```

The `time` figures in section 4 and the kernel's own `Permission denied`
messages in section 7 are written to standard error. To capture a full run
including those, redirect both streams:
`./blast_radius_reproductions.sh > run.txt 2>&1`.

Runs in a few seconds on a local Linux filesystem; file creation may take
noticeably longer on WSL2, overlay filesystems, virtualized or network
storage, or other constrained environments. Checks its own dependencies
before doing anything
else, see "0. Preflight" below for exactly what that checks and prints.
Every section creates its own directory under `/tmp` with `mktemp`, using a
distinctive prefix per section rather than a random name alone. Every one of
those is registered in a single array and removed by one top-level trap at
actual script exit, rather than each section managing its own trap; an
earlier version did the latter, and it silently leaked one directory per run
in the reversibility section, cleaned up only on an early failure, never on
the normal successful path. Caught by checking `/tmp` after a run instead of
trusting the exit code, fixed by the rewrite. All files and directories the
demonstrations create live under
`/tmp`. A normal completed run leaves nothing behind under `/tmp`, confirmed by
clearing everything, running once, and checking again immediately after.
The script does read a few things outside `/tmp` in the ordinary course of
the demonstrations, `/etc/passwd`, `/etc/group`, and standard command
version output, but doesn't write to or modify anything outside `/tmp`.

## What each section proves

Each numbered section, 1 through 7, prints a one-line "why this matters"
statement right after its header, so someone running this without the
article open still gets the point of what they're about to see.

0. **Preflight**, the actual code, not a description of it. `wc`, `cut`, and
   `head` were added to the required-commands list after one external
   review found the script used them without checking for them first; a
   second review then found the same gap again for `rm`, `chmod`, `chown`,
   `mkdir`, `touch`, `id`, `uname`, and `getent`, all genuinely invoked,
   none previously checked. Rather than keep closing this one name at a
   time as reviewers happen to spot the next gap, every external command
   the script invokes during the demonstrations and preflight itself is
   now in this list (the shebang's own `env` isn't, since that's what
   launches the script, not something the script calls):

   ```bash
   require_cmd() {
     command -v "$1" > /dev/null 2>&1 || { echo "ERROR: required command not found: $1" >&2; exit 1; };
   };

   echo "==================================================";
   echo "0. Preflight: required commands, environment, and uid 65534";
   echo "==================================================";
   for cmd in python3 find xargs sort tr sha256sum mktemp mv seq wc cut head rm chmod chown mkdir touch id uname getent stat bash; do
     require_cmd "$cmd";
   done;
   echo "all core commands found: python3 find xargs sort tr sha256sum mktemp mv seq wc cut head rm chmod chown mkdir touch id uname getent stat bash";

   # Section 3 calls Executor.shutdown(cancel_futures=...), added in Python 3.9;
   # on 3.8 or earlier this fails with a TypeError partway through the run
   # instead of at this preflight check. Caught here instead.
   python3 -c "import sys; sys.exit(0 if sys.version_info >= (3, 9) else 1)" || {
     echo "ERROR: Python 3.9 or newer required (section 3 uses Executor.shutdown(cancel_futures=...), added in 3.9); found $(python3 --version 2>&1)" >&2;
     exit 1;
   };

   if command -v findmnt > /dev/null 2>&1; then
     FINDMNT_AVAILABLE=1;
   else
     FINDMNT_AVAILABLE=0;
     echo "note: findmnt not found; section 4 will run but skip printing the filesystem type.";
   fi;

   if command -v setpriv > /dev/null 2>&1; then
     SETPRIV_AVAILABLE=1;
   else
     SETPRIV_AVAILABLE=0;
     echo "note: setpriv not found; section 7 will be skipped even if run as root.";
   fi;

   echo;
   echo "user: $(id)";
   echo "kernel: $(uname -sr)";
   printf 'python3: '; python3 --version;
   printf 'find: '; find --version | head -1;
   printf 'mv: '; mv --version | head -1;
   if [ "$FINDMNT_AVAILABLE" -eq 1 ]; then
     printf 'findmnt: '; findmnt --version | head -1;
   fi;
   if [ "$SETPRIV_AVAILABLE" -eq 1 ]; then
     printf 'setpriv: '; setpriv --version;
   fi;

   echo;
   echo "uid/gid 65534, used in section 7:";
   getent passwd 65534 || echo "  no passwd entry for 65534 on this system (fine, setpriv accepts a bare numeric uid directly; the name assigned to 65534, if any, varies by distribution and version)";
   getent group 65534 || echo "  no group entry for 65534 on this system (fine, same reason)";
   ```

   Every required command listed there is verified against this exact
   script by actually breaking it: removing `sha256sum` from `PATH` gets
   `ERROR: required command not found: sha256sum` and an immediate exit,
   removing `setpriv` gets sections 1-6 running normally and section 7
   skipping with its own message, both confirmed by running it, not by
   reading the code and assuming. The Python version check is verified the
   same way, against the check's own logic rather than by installing a
   second interpreter: `python3 -c "import sys; sys.exit(0 if (3,7) >=
   (3,9) else 1)"` exits 1, `python3 -c "import sys; sys.exit(0 if (3,9)
   >= (3,9) else 1)"` exits 0.

1. **Cap test**: executes the actual parameter-expansion collapse (an
   unset path variable resolving to an unintended location) and prints the
   resolved path, not just a narrated description of one. The path counted
   as the "collapsed" candidate set is not a same-named directory built in
   parallel: it's produced by literally concatenating the real computed
   collapse string onto a sandboxed stand-in for the real filesystem root
   (the script never touches the real `/`), so the count is mechanically
   derived from the expansion, not just labeled to resemble it. Also shows,
   executed, that `set -u` catches an unset variable but not an
   empty-but-assigned one. Both candidate counts are null-delimited rather
   than piped through `wc -l`, matching the extent section's own standard.
   The two counts are arbitrary by construction, since that's the actual
   finding: a cap can't distinguish two candidate sets that both land
   under the threshold, regardless of which one is the failure. The script
   asserts both counts against their fixed expected values and asserts
   both land under the cap, exiting 1 on either mismatch, rather than only
   printing PROCEED and leaving the reader to check it.
2. **Extent**: a shell glob without `dotglob` silently omits dotfiles;
   `find` doesn't. Counted with array expansion, not `ls | wc -l`, and the
   `find` count itself is null-delimited rather than piped through `wc -l`,
   both known landmines on unusual filenames. The script asserts the two
   counts against their fixed expected values (4 and 2) and exits 1 on a
   mismatch.
3. **Rate**: reports three states at a 400ms observation deadline,
   completed, in progress, and queued, rather than collapsing the last two
   into one "untouched" number. This observes state at a fixed point; it
   does not simulate an interrupt, and "in progress" means started but
   not yet complete, not a claim about whether that work can still be
   stopped. Exact counts shift a little with scheduler
   timing; that's expected and stated, not a defect.
4. **Reversibility**: a directory rename doesn't recursively process
   every child entry; a recursive delete does. This section round-trips the
   data, renames out and back, and compares a manifest built from each
   file's actual content hash, not just filename and size, so two
   same-sized files with different contents would actually be caught. The
   manifest hash changes every run by design (file content includes
   `$RANDOM`); what's checked is that the before and after hashes match
   each other, not a fixed reference value. The quarantine directory is
   created fresh with `mktemp -d` rather than a predictable PID-based
   name, so cleanup can never remove a path this invocation didn't create.
   Prints the kernel and `mv` version alongside the timing, and separately
   verifies, rather than just names, the same-filesystem condition the
   result depends on: it compares the actual numeric device id (`stat -c
   '%d'`) for the original directory and the quarantine directory, prints
   both, and exits with an error if they differ, rather than reporting one
   side's filesystem type and asking you to trust the other matches.
   Matching device ids confirm the two directories share the same
   underlying device in this controlled run, both created directly under
   `/tmp`; it isn't a claim that any two same-device paths will always
   rename successfully across arbitrary mount topology, since Linux can
   mount one filesystem at multiple points and still refuse a rename
   across them. An earlier version compared `findmnt`'s SOURCE string
   instead, which is usually adequate but is a step further from what the
   kernel actually checks than the device id is.
   Filesystem reversibility isn't full
   system-state reversibility; the article says so and this script
   doesn't attempt to test the difference, including one specific case
   worth naming: a process already writing to a file when the directory
   moves keeps writing into it, uninterrupted, since Linux tracks an open
   file by inode, not the path that named it at open time. The script
   exits 1 if the before/after manifest hashes don't match, rather than
   only printing `match: no` and leaving the round-trip claim unenforced.
5. **Detectability (canary)**: closed-form arithmetic, `1-(1-p)^n`, not
   a field measurement, under an explicit independent-sampling assumption.
   Included for completeness, not because it needed reproducing.
6. **Direction**: a fault confined to one named configuration is guaranteed
   to be sampled by the stratified construction used here, while random
   sampling can miss it even at larger sample sizes. Seeded, so this run's output matches every other run's on the same
   Python version; `random.sample`'s algorithm isn't cross-version-stable
   the way `random()` itself is. The 100%
   stratified figure is exact by construction, not a strong result on its
   own; the random-sampling figures are the actual evidence. The script
   asserts the stratified hit count equals the trial count, so a miss
   there (config D excluded from a 1-per-config draw) would be caught as
   a broken construction rather than reported as a surprising result.
7. **Structural limits**: a kernel-enforced permission boundary holds
   regardless of what the job's code does or doesn't check for. It bounds
   the maximum a failure can reach; it doesn't prevent damage that stays
   inside the boundary it grants. Uses numeric uid 65534 directly rather than the
   name `nobody`, because UID-to-name mappings vary by distribution and
   version.
   That naming difference doesn't affect this demo: `setpriv --reuid`
   accepts a bare numeric uid directly and works whether or not that
   number has a name in `/etc/passwd`, confirmed by testing against a uid
   with no passwd entry at all. What matters is that 65534 isn't 0 (root)
   and isn't the file owner, not that it resolves to a name. Changing a
   process's uid doesn't by itself touch its inheritable or bounding
   capability sets, `setpriv(1)` says so directly, so the demo also drops
   those explicitly (`--inh-caps=-all --bounding-set=-all --no-new-privs`)
   rather than
   relying only on the uid change: the permitted, effective, and ambient
   sets are already cleared by the kernel on a root-to-nonzero uid
   transition, but the demo doesn't lean on that alone. One limit
   specific to this demo, not the mechanism it's demonstrating: the script
   itself starts as root and only drops to the restricted identity when
   `setpriv` runs, so everything before that line still executes with
   full root authority. Production automation should drop privilege
   before the process starts, a systemd security directive or a
   container's execution policy, rather than trust a running process to
   lower its own authority partway through. The `setpriv` calls in this
   section run inside a subshell that `cd`s to `/tmp` first: without that,
   running the whole script as `sudo -i` from `/root` produces a spurious
   `find: Failed to restore initial working directory: /root: Permission
   denied`, since the restricted identity can't access the directory the
   shell started in. That's noise about the shell's starting directory,
   not the permission boundary being demonstrated, reproduced and fixed
   after a real run surfaced it. The script ends with an explicit result
   summary: `sections 1-6: PASS`, and section 7
   reports `PASS`, `SKIPPED (requires root + setpriv)`, or `FAIL`,
   distinctly, so a skipped section can't be mistaken for a passed one.
   The reasoning behind the first line lives here, not in the script's
   own output, which stays a plain result report: reaching that line at
   all means no command or assertion in sections 1-6 returned a nonzero
   status, under `set -euo pipefail`. For sections 1, 2, 4, and 6
   specifically, that includes their own assertions, since a failing
   assertion exits nonzero the same as a failing command would.
   Sections 3 and 5 have no separate assertion:
   section 5 is closed-form arithmetic with no external input to diverge
   from, and section 3's only structural invariant (the three states
   summing to 40) is asserted per row inside the Python block itself.

## Evidence classification

Not every result here carries the same kind of guarantee. Read each
accordingly rather than treating all of it as equally empirical:

| Result                       | Reproducibility |
|-------------------------------|------------------|
| Shell parameter expansion, `set -u` behavior | Deterministic |
| `find` vs. glob dotfile visibility | Deterministic |
| Canary detection formula | Deterministic (closed-form arithmetic) |
| Manifest hash match, reversibility round trip | Deterministic within one run |
| Stratified vs. random sampling percentages | Seeded, reproducible on a given Python version |
| Concurrency counts (completed/in progress/queued) | Environment- and scheduler-sensitive |
| `mv`/`rm` timing | Single-environment measurement, not a benchmark |
| DAC permission boundary | Environment- and privilege-sensitive (needs root) |

## What these experiments do not prove

They don't establish production failure rates, filesystem-independent
timing, or universal canary behavior. They demonstrate specific mechanisms
under explicitly stated assumptions, on one machine, at one point in time.
The rename/delete timing is measured at a single file count (5,000); it
doesn't demonstrate that rename time stays flat at higher scale, only that
a directory rename doesn't recursively process every child entry, a
separate, well-established property of the operation itself that this
script doesn't independently test. The stratified-sampling result is shown for one fault
distribution, entirely confined to one configuration; a fault split across
multiple configurations would narrow stratification's advantage, and this
script doesn't simulate that case. Section 7 demonstrates a POSIX uid
boundary specifically; it says nothing about namespaces, cgroups, or RBAC
policies, which enforce the same underlying principle at container and
platform scale but aren't tested here.
